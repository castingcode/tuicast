Concurrency model

Each session should have one goroutine owning:

- transport reads and writes
- parser state
- mutable screen state
- waiter notification
- shutdown transitions

External callers receive immutable screen snapshots. This avoids exposing locks and makes waits deterministic.

Automation can initially live directly on Session:

session.Send(...)
session.SendKey(...)
session.Screen()
session.WaitFor(...)
session.Close()

A separate Automation type should only be introduced if that responsibility becomes substantial.

Dependency recommendations

Adopt: golang.org/x/crypto/ssh

This is the clear SSH choice. It supports interactive sessions, PTY requests, window resizing, host-key verification, passwords, public keys, and keyboard-interactive authentication. Implementing SSH locally would be unjustifiable.

Strong candidate: github.com/charmbracelet/x/ansi

This provides a maintained DEC/ANSI state-machine parser covering CSI, OSC, DCS, partial sequences, graphemes, and modern xterm extensions.

Use it for tokenization, not as TUICast’s domain model. TUICast should own:

- screen state
- cursor and margins
- VT220 character sets
- device responses
- snapshots and revisions
- deterministic automation semantics

ANSI parsing looks simple until arbitrary network chunk boundaries, cancellation characters, malformed sequences, OSC/DCS termination, UTF-8, and 8-bit controls are included. Reusing a parser is worthwhile.

Evaluate, but do not commit yet: github.com/charmbracelet/x/vt

It is a complete emulator with screen cells, cursor state, alternate screens, scrollback, input generation, and xterm behavior. However, it is explicitly experimental and currently lacks a stable release contract. Its abstractions may also pull TUICast toward a modern xterm renderer rather than precise legacy VT220 automation.

I recommend a short spike against captured WMS transcripts before choosing between:

1. x/ansi parser + TUICast-owned screen interpreter, or
2. wrapping x/vt.

My current preference is option 1.

Avoid initially: github.com/hinshun/vt10x

It offers a full screen model, but its latest documented revision is from 2022, has no stable tagged version, exposes its own locking, and uses log.Logger. That conflicts with TUICast’s slog and session-ownership model.

Implement Telnet negotiation locally

The available Telnet packages are either older or shaped mainly as client/server frameworks. TUICast needs fine-grained control over:

- IAC escaping
- DO/DONT/WILL/WONT
- terminal type (TTYPE)
- window size (NAWS)
- echo and suppress-go-ahead
- binary mode
- subnegotiation
- negotiation loops and fragmented input

A focused RFC 854 state machine is small enough to own and is central to interoperability. It can remain behind io.Reader/io.Writer-style transport boundaries.

Yes. The key is distinguishing an SSH network connection from an SSH session channel.

SSH supports multiple interactive sessions over one authenticated TCP connection. OpenSSH defaults MaxSessions to 10 per connection, which closely matches your observed limit.

Recommended approach

Use a pool of authenticated SSH connections, with several session channels on each:

                     ┌─ SSH connection 1 ─ sessions 1–10
TUICast session pool ├─ SSH connection 2 ─ sessions 11–20
                     ├─ SSH connection 3 ─ sessions 21–30
                     └─ ...

With default OpenSSH limits, 200 sessions require roughly 20 connections. If the server permits 25–50 channels per connection, use fewer connections—but avoid putting all 200 sessions on one connection because its failure would terminate everything.

For TUICast, I would design the SSH adapter with configurable limits such as:

- maximum authenticated connections
- target sessions per connection
- bounded concurrent connection establishment
- retry/backoff for transient handshake rejection
- replacement of failed connections
- load distribution across connections

The server does not expose MaxSessions through the SSH protocol, so this must be configured conservatively and adjusted when channel creation is rejected.

Two different OpenSSH limits

According to the [OpenSSH configuration documentation](https://man.openbsd.org/sshd_config):

- MaxSessions defaults to 10 and limits shell/login/subsystem channels per authenticated network connection.
- MaxStartups defaults to 10:30:100 and controls concurrent unauthenticated connections. Once 10 handshakes are in progress, random rejection begins; at 100, all new attempts are rejected.

Therefore:

- Failure opening the 11th channel on one connection suggests MaxSessions.
- EOF/reset during bursts of new connections suggests MaxStartups, a firewall, or rate limiting.
- TCP “connection refused” generally points elsewhere, not MaxSessions.

A connection pool should establish connections gradually—perhaps 2–5 handshakes concurrently—rather than dialing 20 or 200 simultaneously.

If you control the server

You can tune sshd_config, for example:

MaxSessions 50
MaxStartups 20:30:100

The exact values should be load-tested. Raising them increases resource consumption and potentially expands denial-of-service exposure.

Also inspect:

- PAM maxlogins limits
- per-user process and file-descriptor limits
- systemd task limits
- PTY availability
- memory and CPU
- firewall/fail2ban/per-source restrictions
- WMS application session or license limits

TUICast design implication

The high-level API should acquire a logical session from an SSH connection pool rather than creating a fresh TCP connection for every session. Telnet can use the same orchestration abstraction while using one network connection per session.

For a target of 200 sessions, a sensible starting profile would be:

- 20–25 authenticated connections
- 8–10 sessions per connection
- at most 4 concurrent handshakes
- reconnect with exponential backoff and jitter

That works with default MaxSessions, avoids MaxStartups bursts, and limits each connection’s failure blast radius.
